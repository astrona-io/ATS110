# Testing Schemas With percli

A schema is code, and code that is not tested breaks without anyone noticing. Someone removes `close` to allow one more field, someone changes `>=0` to `>0`, and nothing fails until a dashboard author hits the problem. `percli plugin test-schemas` closes that gap. It runs a set of example files against the schema: files that must be accepted and files that must be refused. This part shows where the files go, how to write good ones, and how to run them.

## Where the tests go

Tests live next to the schema they test, in a folder named `tests`. For the module you are working in, the schema is `schemas/panels/status-badge/status-badge.cue`, so the folders are:

- `schemas/panels/status-badge/tests/valid` holds files the schema must accept.
- `schemas/panels/status-badge/tests/invalid` holds files the schema must refuse.

Each test is one JSON file. The file holds the whole definition, with `kind` and `spec`, the same shape as the example file next to the schema. `percli` unifies the file with the schema. A valid test passes when that succeeds, and an invalid test passes when it fails.

A module with a migration schema, which converts Grafana panels, can also hold migration tests in a `migrate/tests` folder. Each is a folder with an `input.json` and an `expected.json`. This module has no migration schema, so only the first two kinds apply.

## Write tests that each prove one thing

A good test changes one thing. If an invalid file has an empty label and a negative limit at once, it passes as soon as either rule exists, and it hides the case where one rule is missing. Give each file one fault and a name that says what the fault is.

For a `StatusBadge` schema with a label of 1 to 40 characters, limits of 0 or more, a `format` of `number` or `percent`, and a closed spec, a useful set is:

| File | Folder | What it proves |
| --- | --- | --- |
| `basic.json` | valid | The normal case is accepted |
| `zero-limits.json` | valid | The boundary 0 is allowed by `>=0` |
| `percent.json` | valid | The second allowed `format` is accepted |
| `empty-label.json` | invalid | `strings.MinRunes(1)` refuses an empty label |
| `negative-warning.json` | invalid | `>=0` refuses a negative limit |
| `bad-format.json` | invalid | The list of `format` values is enforced |
| `extra-field.json` | invalid | `close` refuses an unknown field |
| `missing-critical.json` | invalid | A required field cannot be left out |

Test the boundaries as well as the middle. A label of exactly 40 characters belongs in the valid folder and one of 41 in the invalid folder. Those two files fail the moment someone changes 40 to 39 or 41.

## Run the tests

Save this as `basic.json`, a valid test:

```json
{
  "kind": "StatusBadge",
  "spec": {
    "label": "Targets up",
    "warning": 1,
    "critical": 0
  }
}
```

Save this as `empty-label.json`, an invalid test:

```json
{
  "kind": "StatusBadge",
  "spec": {
    "label": "",
    "warning": 1,
    "critical": 0
  }
}
```

Save the tightened schema as `status-badge.cue` (the version with `strings.MinRunes`, `>=0` and `format?`), then copy it and the two files into the module. The `mkdir -p` makes the test folders:

```sh
plugin_builder() { kubectl -n perses exec -i deploy/plugin-builder -- sh -c "cd /workspace && $*"; }
SCHEMA_DIR=status-badge/schemas/panels/status-badge
plugin_builder "mkdir -p $SCHEMA_DIR/tests/valid $SCHEMA_DIR/tests/invalid"
kubectl -n perses exec -i deploy/plugin-builder -- sh -c "cat > /workspace/$SCHEMA_DIR/status-badge.cue" < status-badge.cue
kubectl -n perses exec -i deploy/plugin-builder -- sh -c "cat > /workspace/$SCHEMA_DIR/tests/valid/basic.json" < basic.json
kubectl -n perses exec -i deploy/plugin-builder -- sh -c "cat > /workspace/$SCHEMA_DIR/tests/invalid/empty-label.json" < empty-label.json
plugin_builder "cd status-badge && percli plugin test-schemas"
```

The command finds every `tests` folder in the module, runs each file, and prints one line per file. Each line names the file, says whether the test is a valid or an invalid one, and shows the path. After the lines it prints a summary that says how many tests ran and whether all of them passed. The command exits with a non-zero status when a test fails, so a script or a CI job can rely on it.

By default the command works on the folder where you run it. To test a module somewhere else, pass `--plugin.path ./status-badge` and run it from the parent folder. If you keep the plugin configuration in a file other than `perses_plugin_config.yaml`, the flag `--config` names it, relative to the plugin path. A module generated by `percli` works without that file.

## Prove that a test can fail

A test that cannot fail proves nothing. The simplest check is to break the schema on purpose and see the test notice. Remove `close(` and its closing `)` from a scratch copy of the schema in the playground, or change `>=0` to `number`, and run the command again. The invalid test for that rule now fails, because the schema accepts what the test says it must refuse. Put the schema back and run it again: the line is green. The habit costs a minute and shows that each test reaches the rule it names.

## Run schema tests with the other checks

Schema tests are cheap, so run them often. A sensible order for a module is `percli plugin lint` for the format of `package.json` and the schema, then `percli plugin test-schemas` for the behaviour of the schema, then the build. Neither of the first two needs `node_modules`. A schema fault found by `test-schemas` takes a second to fix. The same fault found after an install, which needs a restart of Perses, takes minutes.

## Common pitfalls

> [!WARNING]
> - **Putting a test outside `tests/valid` or `tests/invalid`.** A file anywhere else is never run, and the summary still says all tests passed.
> - **Writing only the `spec` in a test.** The file must hold `kind` and `spec`, because the schema describes both.
> - **Packing several faults into one invalid file.** The test passes while one rule is missing.
> - **Writing tests that only match what the schema does today.** Write them from the requirement, then see whether the schema meets them.
> - **Trusting a green run without a red one.** Break a rule once to see that its test fails.

You can now write a schema and keep it honest with tests. What remains is reading the failures when the tests and the schema disagree.
