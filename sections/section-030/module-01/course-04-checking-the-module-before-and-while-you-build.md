# Checking The Module Before And While You Build

A build that runs for several minutes and then fails on a typo is slow feedback. `percli` has two commands that give faster feedback: `percli plugin lint` checks the module without building it, and `percli plugin start` runs a development server so that changes show in Perses while you edit. This part shows what each does, when to use it, and what it does not check.

## Check the module with lint

`percli plugin lint` reads the module and checks its format and configuration. According to its help text it checks three things: the structure of `package.json` and its `perses` section, whether a CUE model schema exists and is correct when the plugin needs one, and whether a migration schema is correct if the module has one.

Run it from the module folder, or give the folder with the flag `--plugin.path`:

```sh
plugin_builder() { kubectl -n perses exec -i deploy/plugin-builder -- sh -c "cd /workspace && $*"; }
plugin_builder "cd status-badge && percli plugin lint"
plugin_builder "percli plugin lint --plugin.path ./status-badge"
```

Both lines do the same check. By default the command looks for a file named `perses_plugin_config.yaml` in the module; the flag `--config` names a different file, relative to the plugin path. A module generated by `percli` works without this file.

Lint needs no `node_modules` and starts no build. It is quick, so it is worth running after every change to `package.json` or to a `.cue` file.

What lint does not check: the React code. A type error in `StatusBadge.tsx` is found by `npm run build`, not by lint. It also does not run the schema against sample settings. That is the job of `percli plugin test-schemas`, which the next module covers.

## A sensible order

Run the checks from cheapest to dearest:

1. `cue mod tidy` after any change to the imports of a schema.
2. `percli plugin lint` for the format and the schema.
3. `npm run build` for the types and the bundle, or `percli plugin build` for the archive as well.
4. Install the archive and look at `/api/v1/plugins`.

If a step fails, fix it before going on. A failure at step 4 is the most costly to debug, because it needs a restart of Perses.

## Live development with start

`percli plugin start` is made for developing on your own computer against a running Perses. Its help text says it runs the npm script of the module that holds `rsbuild dev`, finds the port and the plugin name, and then sends the configuration to the Perses server. Perses contacts every development server it was told about and shows the plugin in its interface.

The command takes one or more module folders, or `--all` for a monorepo:

```sh
percli plugin start
percli plugin start ./plugins/status-badge
percli plugin start --all
```

Three conditions must hold:

- `percli` is logged in to the Perses server, with `percli login`, because it sends the configuration there.
- The Perses server accepts development plugins. This is a setting of the server, in the `plugin` section of its configuration. Read the configuration reference of your Perses version for the exact key, and do not turn it on in production.
- The browser and the Perses server can both reach the development server's port.

The third condition is why this guide builds in the cluster instead: the playground pod `plugin-builder` has no route from the browser to its development port. On a laptop, with Perses on the same machine, all three hold.

What you gain: a change to the component shows on reload, with no archive, no volume and no restart. What you do not gain: an installed plugin. The development entry exists only while the command runs. When it stops, Perses forgets the plugin, and the real install is still the archive.

## Pick the right tool

| You want to | Use |
| --- | --- |
| Check `package.json` and the schemas quickly | `percli plugin lint` |
| Check that the React code compiles | `npm run build` |
| Produce the file Perses installs | `percli plugin build` |
| See component changes live while you edit | `percli plugin start` |
| Check the schema against sample settings | `percli plugin test-schemas` |

## Try it

1. Run `percli plugin lint` in the `status-badge` module. It should pass.
2. Open `package.json` and change the value of a field inside the `perses` section, such as the plugin kind, to something that does not match the schema folder. Run lint again and read the message.
3. Put the value back and run lint again.

The builder pod has `percli` 0.54.0. If a command in this part is missing there, `percli plugin --help` lists the commands that version has.

## Common pitfalls

> [!WARNING]
> - **Expecting lint to find React type errors.** It reads the module format and the schemas. The TypeScript compiler finds the rest.
> - **Leaving `percli plugin start` running and expecting an installed plugin.** The entry exists only while the command runs.
> - **Enabling development plugins on a shared server.** The server then contacts addresses it was given by a client.
> - **Checking only after the build.** Lint finds a broken schema in a second, and the build takes minutes.

```sh
astrona stop ats-110-playground-030-01
```

Then start the lab:

```sh
astrona run --git ssh://git@github.com/astrona-io/ATS110.git -c sections/section-030/module-01/labs/lab-01
```

The task is on the next page. Solve it on your own first. When you think you are done, send it for grading:

